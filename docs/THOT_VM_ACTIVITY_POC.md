# Thot VM activity POC

**Status:** Project-defined test model implemented. The latest workspace changes compile; VirtualBox execution has not been exercised in this environment because VirtualBox is unavailable.

This POC runs teacher-defined checks against OVA deliveries on one Linux host with VirtualBox. It records technical test results and evidence and calculates rubric scores from checks and final evaluation marks from rubric groups. Project-scoped student rosters and manual or suggested delivery assignments are supported.

## Project bundle

A project can be a `.thot.zip`, `.thot.tgz`, or `.thot.gz` archive with `configuration.yaml` at its archive root, or an unpacked project directory with that file at its root. External teacher scripts are stored in the project. For example:

```text
linux_competition.thot.tgz
├── configuration.yaml
└── extern/
    └── tests/
        └── vm_start_time.py
```

The configuration defines an ordered test list. A test reference has the form `Platform/test_name`, such as `VirtualBox/import_ova` or `ssh/get_host_info`; a teacher-provided script uses `extern/<archive-relative-path>`. Tests may set scalar `parameters`, a per-test `timeout` in seconds, `requirements` naming earlier tests, and `repeat`. A repeated test produces names such as `start_time_01`, `start_time_02`, and `start_time_03`. Requirements run only when all repetitions of each required test pass.

An optional root `students.csv` may define the project's roster. It is imported automatically when a run is created, and rows are stored under that project. The CSV must include name and email columns; common English, Spanish, and Catalan header aliases are accepted. A missing or blank external-ID value is replaced with the student's email, so every stored project student has an external ID. CLI student import and retrieval commands also require a current project and include its ID, name, and path in their responses.

The example project is [configuration.yaml](../examples/vm-activity-poc/configuration.yaml). Its tests import an OVA, run the external HTTP startup and screenshot check three times, start the VM, collect host information over SSH, stop it, and destroy it. The external script receives parameters as `key=value` arguments and gets `THOT_ARTIFACT_DIR`, `VBOX_USER_HOME`, and `VBOX_MANAGE_PATH` environment variables. Its stdout, stderr, and process exit code are recorded. Internal tests return the same three values through the engine result contract.

See the [implemented tests, checks, rubrics, and evaluation reference](IMPLEMENTED_CATALOG.md) for the complete built-in inventory, parameters, and result behavior.

The loader snapshots project contents before execution. For directory projects, it excludes the configured delivery directory from the immutable project snapshot; relative project paths resolve from the project directory. For archives, relative paths resolve from the archive's containing directory. Absolute delivery paths are accepted when readable by the daemon. Project `vm_path` remains relative to the project location and must resolve safely beneath it.

Built-in tests also include `libguestfs/disk_info`, `libguestfs/linux_rootfs_info`, and `libguestfs/linux_tinycore_info`. These inspect disk images offline using libguestfs tools. `disk_path` is required and may name a disk image or a directory; optional `disk_name` selects one image when the directory contains several. `linux_rootfs_info` reports information for the Linux root partition identified by libguestfs. `linux_tinycore_info` detects Tiny Core's compressed CPIO boot image and reports information available from its base initramfs and boot-storage partition. The daemon must have `libguestfs-tools` executables on its `PATH`.

`network/nmap` invokes the system `nmap` executable with an unprivileged TCP connect scan and service/version detection; the service account must have `nmap` installed and on its `PATH`. It scans Nmap's top 1000 TCP ports by default. Set `ports` to a comma-separated list/range (for example `22,80,8000-8100`) or `top_ports` to change the scan. Set `exclude-ports` to a comma-separated list/range to pass Nmap's `--exclude-ports` option; this can be combined with either scan selection. The raw Nmap report is captured as stdout, and parsed open-port/service details are also stored in `observation`. The stats tests consume results already recorded earlier for the same delivery. Their `tests` parameter accepts a configured test name or a comma-separated list of names; a repeated test name selects all its repetitions. `property` names the field to extract, and `regex` or `JSONPath` selects the value. `data_type` is optional and defaults to `number`. The tests write a YAML summary to `stdout`, with `count`, `max`, `min`, `freq` (mode), `avg`, `var`, `std`, and p1/p5/p10/p20/p30/p40/p50/p60/p70/p80/p90/p95/p99 percentiles for numeric data. Text, date, and datetime summaries include max, min, and freq. This test family summarizes earlier test results; the separate `stats/...` checks compare a delivery's value with a run-wide statistic. The code is divided by platform under `crates/thot-engine/src/tests/`; adding a platform requires a dispatcher and its own module. Unknown platform/test references fail as test errors.

## Run behavior and limits

The CLI accepts either a project path directly, for example `thot run create /srv/course/linux_competition.thot.tgz`, or discovers one when run with no subcommand. Bare `thot run` selects exactly one `.thot.gz`, `.thot.tgz`, `.thot.zip`, or root `configuration.yaml` from the current directory and reports ambiguity when more than one is present. `thot run list` lists saved runs. `thot run status` resolves the run only when exactly one run is queued, running, or cancelling. Its response includes one expedient per student with the assigned delivery filename and a lifecycle status of `pending`, `running`, or `finished`. `thot run delete <run-id>` removes an inactive run and its related database records. Queued, running, or cancelling runs cannot be deleted. Run IDs use the project name plus its UTC creation time, such as `linux_competition-20261026_154512`; each per-student expedient ID includes its delivery filename, the same timestamp, and the student ID. Successful run and expedient CLI responses are displayed as YAML while the HTTP API remains JSON. Deletion leaves report and VM artifacts on disk until `thot clean` removes data proven to be orphaned.

Run creation selects the current project. Student and assignment commands invoked from a directory containing root `configuration.yaml` select that project's directory; elsewhere they use the most recently selected project. Assignment guess/get/import index the configured delivery folder before a run exists. Guessing compares project students to those deliveries using names, surnames, email usernames and addresses, external IDs, and student IDs, with a second pass that rewards agreement across identity fields. Review suggestions with `thot assignments get`, then replace them with `thot assignments import FILE`. Import resolves each row using only `student_external_id` and `delivery_filename`; other row fields are ignored and populated from current project data. The import response includes the count of valid records and per-record errors with corrections. Valid rows replace the saved mapping; invalid rows are omitted. Students omitted from the mapping and deliveries with no assigned students are skipped during a run. If no assigned student-delivery pairs remain, the run completes without tests or student expedients. Several students can share one delivery; each student has at most one delivery assignment. Guess, get, and import responses identify the project and list unassigned deliveries. A root `assignments.yaml` or `assignments.json` is imported automatically during run creation and replaces saved assignments; having both files is an error.

Run creation creates a pending expedient for each assigned student. During execution, expedients for students sharing a delivery become running together; the tests execute once for that delivery and the resulting report and test evidence are copied to each student's expedient. Each copied report identifies its student while retaining the shared test-result IDs and output. The run-status response lists all of its student expedients and their pending, running, or finished states.

The configured `vm_path` is relative to the archive's containing directory (or the project directory for an unpacked project) and defaults to `./thot_vms`. Thot creates `<vm_path>/<run-id>/<delivery-id>` for each imported VM. The daemon account (usually `thotd`) needs write and execute permission on the existing `vm_path` directory; if it does not exist yet, the account needs write and execute permission on its nearest existing parent to create it. Pre-creating `vm_path` and granting access there avoids granting write access to the project folder. Keep the archive and its scripts protected from modification, and give write access only to the dedicated VM storage location. Do not use a path that overlaps the VirtualBox profile or artifact root.

The daemon runs tests in declared order once per distinct assigned delivery and bounds concurrency by the project setting. All student expedients assigned that same delivery receive a copy of the shared run result. Projects referencing VirtualBox or SSH tests must set concurrency to one while the adapters use shared loopback ports 8080 and 2222. VM checks require those ports to be free. `VirtualBox/import_ova` records VM information and process output but does not grade hardware or network values; an evaluation phase can assess them. After a successful import, the engine separately applies host-isolation settings before later tests run. If that setup fails, the import test remains passed, later tests are skipped, and each assigned student's expedient records the orchestration error.

Projects may define a `checks` list after `tests`. Each check has a unique `name`, optional `description`, internal implementation name in `check`, related configured test name in `test`, and optional scalar `parameters`. The `pass` check returns `1` when the named test passed (all repetitions must pass), or `0` otherwise. `regex_match` reads a scalar `property` from each related test result and returns `1` only when the regex matches every result; it needs only a `regex` parameter and no capture group or comparison fields. `yaml_match` reads a JSON or YAML `property` (structured values such as `observation` are accepted directly) and returns `1` when its `JSONPath` expression selects one or more nodes in every result; a result with no selected nodes returns `0`. For example, `property: observation` with `JSONPath: "$.users[?(@.username == 'bin')]"` checks whether the observation contains a user named `bin`. `regex_extract` reads the configured `property` from each related test result, captures the first regex group, converts it using `data_type`, and compares it with `value` using `condition`. `yaml_extract` reads a result property containing a JSON/YAML document, selects exactly one scalar using a `JSONPath` parameter, then compares that value with `value` using the same conversion and comparison rules as `regex_extract`. For example, `property: observation` with `JSONPath: $.vm_configuration.memory` selects the imported VM's memory value. The run-wide `stats/regex_extract` and `stats/yaml_extract` checks extract one value from each unique tested delivery, calculate the configured statistic, and compare the current delivery's value with it. A repeated test must be named by one expanded result ID, such as `start_time_01`. Supported statistics are `max`, `min`, `freq` (mode; ties choose the smallest value), `avg`, population `var` and `std`, and percentiles `p1`, `p5`, `p10`, `p20`, `p30`, `p40`, `p50`, `p60`, `p70`, `p80`, `p90`, `p95`, and `p99`. Percentiles use linear interpolation between neighboring sorted values. `avg`, `var`, `std`, and percentiles require `data_type: number`; `max`, `min`, and `freq` also accept text, date, and datetime. Supported types otherwise are `number`, `text`, `date` (`YYYY-MM-DD`), and `datetime` (RFC 3339); comparisons accept `<`, `<=`, `>`, `>=`, `==`, and `!=`, while `contains` is available only for text. Conditions may also be `r'<regex>'` (the candidate text matches the regex) or `json'<JSONPath>'` (the candidate JSON/YAML document has a JSONPath match); these predicates do not require a comparison value or data type. A regex that does not match returns `0`; an invalid property, document, JSONPath selection, regex, or captured value is reported in `err`. Each student expedient records check rows under `checks`, with `name`, `description`, numeric `result`, nullable `err`, and an RFC 3339 `date_time`; statistical rows also include `statistic`, `sample_count`, and `student_value`.

Projects may also define `rubrics`, each with a unique `name`, optional `description`, an ordered `checks` list (or `checks_list`), a `calculation`, and optional parameters. Each referenced check must exist. `rubrics_multiplier` (default 1) scales each numeric check result before rubric aggregation; check results remain 0 or 1. Supported calculations are `avg`, `max`, `min`, `median`, `p1`, `p5`, `p10`, `p20`, `p30`, `p40`, `p50`, `p60`, `p70`, `p80`, `p90`, `p95`, `p99`, `weighted_avg`, and `sum`. Percentiles use linear interpolation over the sorted check results; `median` is `p50`. `weighted_avg` requires a `weights` array with exactly one non-negative weight per check, in the same order; weights are normalized by their sum, which must be positive. Rubric results are stored in the expedient's top-level `rubrics` list with input check marks, result, nullable error, and execution time. Root `evaluation` items define unique names, optional descriptions, ordered `rubrics` lists, a calculation, and optional weights. They aggregate rubric marks into final marks and are stored under `evaluation.results`. `evaluation_multiplier` (default 1) scales each evaluation result. Both multipliers must be finite and positive; if both differ from 1, run creation returns a warning because the scales compound. Checks, rubrics, and evaluation items are calculated after tests.

Check results are evaluated after tests and copied with the shared delivery results to each assigned student's expedient. `thot run checks [run-id]` evaluates the saved tests again without running tests; it defaults to the most recently created finished run and replaces each expedient's `checks`, `rubrics`, and final `evaluation.results`. From the same unpacked project directory, the command uses its current configuration; otherwise it uses the run's saved project configuration. If neither defines checks, the command reports that instead of returning empty check lists.

Maintenance commands are available through the CLI. `thot clean` removes only orphan data whose ownership can be established. `thot prune` keeps the latest run per project, requests confirmation, deletes older run records, and then cleans orphaned data. `thot reset` requires a generated six-digit confirmation code and clears Thot runtime/database records while retaining installation configuration, project archives, and original delivery files. Files and VMs whose ownership cannot be proven are preserved and reported.

Reports are available with `thot report runs`, `thot report deliveries [run-id]`, `thot report deliveries tests [run-id]`, and `thot report deliveries checks [run-id]`. Delivery reports default to the newest saved run and aggregate once per unique delivery, including shared group submissions. `thot report runs` includes a per-delivery table for active runs, with status, start/end time, and pending, running, failed, completed, and total test counts. `thot report test_stats`, `checks_stats`, and `rubric_stats` summarize each test/check/rubric across expedients, including outcome or score counts, timing percentiles, and warning signals; `thot report expedients` prints test, check, rubric, and final evaluation result matrices. These commands default to the newest run. The default terminal view is a compact table; `--csv`, `--yaml`, and `--json` select export formats. JSON endpoints are available under `/api/v1/reports/` for runs, deliveries, test_stats, checks_stats, rubric_stats, and expedients.

External tests are executable teacher code. They run as child processes with the daemon's operating-system permissions, bounded by each test timeout and the configured stdout/stderr output limit. The process boundary does not sandbox scripts. Only install project archives from trusted instructors, and run the daemon under a dedicated unprivileged account and VirtualBox profile. ZIP and TGZ extraction rejects traversal paths and links and enforces archive size and entry limits.

## Results and artifacts

Each student expedient is stored under the artifact root and identifies the student and assigned delivery. Students sharing a delivery receive separate report files with the same test results and evidence; the tests and evidence are produced once in the shared delivery directory. Reports contain project and delivery identifiers, test references and statuses, timestamps and durations, stdout, stderr, exit code, diagnostics, evidence references, cleanup status, and overall orchestration status. Rubric results are in `rubrics`; final evaluation items are in `evaluation.results`. Raw test output is also written to files. Artifacts use this layout:

```text
<artifact-root>/<project-id>/<run-id>/<delivery-id>/
├── <delivery>-<timestamp>-student-<student-id>.json
├── <delivery>-<timestamp>-student-<other-id>.json
├── cleanup-manifest.json
└── test_records/
    └── <sanitized-delivery-filename>/
        └── <test-name>/
            ├── stdout.txt
            ├── stderr.txt
            └── artifacts/
```

Teacher scripts should save screenshots and other files under `THOT_ARTIFACT_DIR`. Test statuses distinguish `passed`, `failed`, `skipped`, `timed_out`, and `error`. VM cleanup runs after the configured test list as a manifest-scoped safety step, even when a test fails. A configured `VirtualBox/destroy_vm` test performs that cleanup earlier as part of the test sequence.

## Host requirements and safety

Run the daemon natively on the Linux VirtualBox host; this POC does not support containerized VirtualBox execution. Use a dedicated unprivileged service account, a dedicated `VBOX_USER_HOME`, an administrator-qualified VirtualBox version, and the configured firewall confirmation. Keep guest forwarding bound to loopback and block guest access to unrelated host services and unnecessary outbound destinations. Do not share host folders, clipboard, drag-and-drop, or USB devices with imported guests.

The cleanup manifest records the run, delivery, VM name and UUID, storage path, and archive parent. Cleanup checks VM identity and path ownership before unregistering or removing anything. A failed or interrupted cleanup remains visible in the expedient and requires operator review. These controls reduce accidental host exposure; they do not make arbitrary guest images or instructor scripts safe to run on a general-purpose workstation.
